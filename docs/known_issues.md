# 已知问题与注意事项

## 1. 连接

### 1.1 USB 链路的 U1/U2 已关闭

USB 3 链路的低功耗状态 U1/U2 开着时，电脑会不时复位与板子之间的 USB 链路：断开约 1 s 后恢复，客户端报连接错误，板上串口控制台
（ttyGS0）被挂断，Windows 重新识别网络（NetworkProfile 事件 4003）并重新做 DHCP 续租；没有重新枚举，Windows 系统日志中没有 USB 记录。
两块板都工作在 USB 3 超高速，板上 dwc3 控制器开着 USB 3 链路电源管理（设备树 `snps,usb3_lpm_capable`）时，空闲链路 98 % 的时间处于 U2，
约每秒经过一次 Recovery（DSTS 寄存器的链路状态，0xFE200000 + 0xC70C 的位 21:18）。

两块板的启动设备树因此加了 `snps,dis-u1-entry-quirk`、`snps,dis-u2-entry-quirk`（`os/kernel/make_image_ub.sh`），链路一直处于 U0。
对照（2026-10-31 02:00～14:00）：关闭 U1/U2 的接收板在 12 小时连续传输（10～21 MB/s）中 0 次断开；同期开着 U1/U2 的发射板 2 次，都在最后约 4 小时的连续传输中。此前接收板在使用中 24 分钟内断开过 2 次。
原镜像保存在两块板的 `/root/boot-backup/image.ub.u1u2-on`。

### 1.2 两块板的 USB 序列号相同

两块板的 USB 复合设备序列号都是 `0000`，Windows 无法按序列号区分，第二块板按所在端口识别。两根 USB 线交换端口后，
Windows 中网卡的名称与对应关系可能改变；板子的地址（192.168.3.1 / 4.1）在板上固定，不受影响。

### 1.3 电脑上的连续流：Windows 原生程序收发各 50 MSPS

经 USB 网口的连续流，2026-11-01 实测，`SoapySDRUtil --rate` 50 MSPS。发射只在发射板上测（接收板的 `rx` 镜像没有发射数据通路，
见 2.2，在它上面测发射会得到虚高的数字）。丢失看外壳计数器：接收 `HOST0_RX_OVF`（0x058），发射 `TX_UNDERFLOW`（0x044）。

| 方式 | 接收 | 发射 | 收发同时 |
|---|---|---|---|
| RNDIS 网卡 + iiod（原来） | 20 MSPS 无丢失，上限约 25 MSPS | 未在发射板上测 | |
| NCM 网卡 + glidelink-streamd（UDP），Windows 原生（8000 字节的包） | 49.6～49.8 MSPS，溢出只在开始时 1 次 | 49.9 MSPS，板上丢包 0 | 收 49.1～49.7、发 50.0 MSPS |
| 同上，WSL（1472 字节的包） | 49.3～49.5 MSPS | 约 48 MSPS，丢少量包 | |

- 板上的改动：网卡功能 RNDIS → NCM（`os/board/install_net.sh`）；NCM 每次 USB 传输 16 KB → 约 64 KB（内核补丁 0003）；
  最大帧长 1514 → 9014 字节（补丁 0004，usb0 的 MTU 9000）；NCM 网卡声明校验和卸载、IPv4 UDP 校验和写 0（补丁 0005），
  板上发包可用 UDP 分段卸载；采样流经 `sw/streamd` 的 UDP 流，不经 iiod；USB 中断在 CPU 0，收包协议处理分到 CPU 1～3。
  电脑端 Windows 的 NCM 驱动按板子声明的帧长自动把这两块网卡的 MTU 设为 9000。
- USB 链路与 Windows 的 NCM 驱动不丢包、不乱序（Windows 原生客户端发射 138 万个包，板上全部按序收到）。
- WSL（镜像网络模式）：Windows 与 WSL 之间不传大于 1500 字节的帧（WSL 中网卡显示 MTU 9000，`ping -M do -s 4000` 不通），
  并且高速时会丢 UDP 包、偶有乱序（约 0.2 %，板上没有丢，丢在到达板子之前）。WSL 中要先把连板子的网卡设为 MTU 1500
  （`sw/pc/wsl-board-mtu`，见 `docs/pc_setup.md`），这时只能用 1472 字节的包，发射到不了 50 MSPS；高采样率用 Windows 原生程序。
- 1472 字节的包收发同时各 50 MSPS 时板上每秒要收约 14 万个包，发射约 43、接收约 40 MSPS；8000 字节的包没有这个问题。
- 被强行终止的 Soapy 程序（如被杀掉的 `SoapySDRUtil`、GRC 停止按钮结束的流程图）不会关闭流，主机端口 0 / 1 的包头模式
  （`CONFIG` 位 2 / 3、4 / 5）会留着。经 Soapy 模块再开流时按新流的设置重写，不受影响；直接用 libiio 的原始数据流会把数据当成
  包头处理（发射方向被当成无效包丢掉，数字虚高），这类程序要先清这些位（如 `sw/tests/ramp_loopback_iio.c`）。
- 第 2 阶段（U1/U2 关闭之前）经 iiod 只有约 5 MSPS 无丢失、上限 7.3 MSPS。

## 2. 射频

### 2.1 同一块板的发射本振漏进接收

发射本振与接收本振设在同一频率时，本板发射本振的泄漏出现在接收数据中，位于约 −0.6 kHz 处、约 −53 dBFS，与载频无关
（两个合成器的小数分频量化不同）。只接收的场合把本板的发射本振移开：MATLAB `rx.config(RxFreq=f, TxFreq=f + 10e6)`。
弱信号或依赖最强谱线的处理（如频偏校正例程的寻峰）受它影响最大。

### 2.2 接收板的镜像没有发射数据通路

`glidelink_rx` 镜像中主机端口 0 的发射方向没有接到 DAC：接收板发出的只有本振泄漏。一块板上既发又收用发射板，或给接收板换镜像。

### 2.3 天线与环境

- 天线按 915 MHz 设计：2.4 GHz 的链路比 915 MHz 弱约 25 dB；调频广播波段（76～108 MHz）只能收到强台。
- 915 MHz 附近（接收板）在 −7.5 MHz、+5.6 MHz 处有窄带干扰，另有时有时无的突发干扰，紧邻 GSM 900 上行频段，来源未确认。
- 2.4 GHz 有大量 WiFi 包：其中的 802.11a/g 包会被 OFDM 接收机检测到，接收端要按长度、格式或帧内容区分。
- 发射板设置频率或带宽时，AD9361 的发射正交校准会发出 15～20 ms 的连续信号。

### 2.4 采样率

- 上限 50 MSPS：第三方子卡的 TX 数据接口在 61.44 MSPS 下余量不足（`hw/README.md`），Soapy 模块拒绝更高的采样率。
- 下限 0.52 MSPS（AD9361 加 FIR 抽取）。ADALM-Pluto 能到 65 kSPS 是因为它的 FPGA 另有抽取，移植 Pluto 例程时采样率要提高。

### 2.5 FIR 已打开时换 FIR 文件，时钟链不跟着变

- AD9361 驱动只在 FIR 从关到开时套用 FIR 文件里的时钟链（`RRX` / `RTX` 行）。FIR 已经打开时写 `filter_fir_config` 再写
  `in_out_voltage_filter_fir_en=1`，驱动换上新的系数与插值 / 抽取倍数，时钟链却保持原样。
- 桥接服务的客户端（MATLAB、GNU Radio）经 libad9361 设 20 MSPS 后，FIR 按 ×4 打开，发射时钟链是 `DAC 320 → 160 → 80 → TF 80 MHz`。
  之后再启动脱机 DeepJSCC-Q 系统，竞赛的 ×2 FIR 装进去了，时钟链仍是 `TF 80 MHz`（应为 40 MHz），发出的信号是坏的：
  2026-10-31 实测强信号下数据辅助 SNR 只有 7.5 dB（应为 37 dB），div2k_0802 的 PSNR 约 26 dB（应为 32.2 dB），
  而且不随发射功率变化；接收板时钟链错时同样如此。
- 守护程序（`sw/offline/glidelinkd.py`）现在先关 FIR、写文件、再打开，并核对 `rx_path_rates` / `tx_path_rates` 与文件一致，
  不一致时启动失败。改正后同样的条件下：额外衰减 0 dB 时 PSNR 32.21 dB、数据辅助 SNR 33～37 dB。
- 自己写 FIR 文件的程序同样要先写 `in_out_voltage_filter_fir_en=0`。

### 2.6 接收端星座图显示占用解码器输入

- 接收应用的 `symbols` 命令（gr-glidelink 的 JSCC RX Symbols、`jscc_video.grc` 的星座图）取符号时，主机端口 1 暂时改接 OFDM 接收机的输出，
  解码器的输入断开。每次取符号少 2～3 幅解码图，之后还会收到 1 个 32768 字的符号包，接收应用把它记为 `bad_packets`。
- 星座图每约 2.3 s 取一次时，解码帧率约 28.3 帧/s（OFDM 接收机仍是 30 帧/s）；需要满帧率时关掉星座图。

### 2.7 先打开 FIR、后切换增益模式，接收通路变弱约 20 dB

- 开机后 AD9361 的接收增益模式是慢速 AGC（设备树默认）。脱机接收板第一次启动时，守护程序原先先打开 FIR（驱动随之重新校准接收通路），
  再把增益模式切成快速 AGC。这样设置后，同样的信号下快速 AGC 停在约 50 档（45～52 dB），正常是约 29 档（26～28 dB）；
  看门狗不动作（同步率正常），手动复位 AGC 也回到同一档。解调出的帧约 1/4～1/2 是噪声（判决 EVM −6～−8 dB，
  与发送符号不相关），解码成彩色噪声纹理，PSNR 约 9 dB；其余帧 28～32 dB。
- 守护程序重启时增益模式已是快速 AGC，FIR 关开后的校准就在最终模式下进行，所以不出现；FIR 关开一次也能恢复。
  两种状态的寄存器差别在直流 / 正交校准结果与接收基带滤波器设置（0x1C3、0x1E4、0x1F3 等）。
- 守护程序现在先设增益模式，再关开 FIR。验证：开机后的状态（慢速 AGC、30.72 MSPS、18 MHz 带宽）启动 3 次、真实重启 1 次，
  全部无坏帧；重启后逐帧 PSNR 在额外衰减 0 / 4 / 10 dB 时 p10 为 32.19 / 32.18 / 32.11 dB，解码 29.99 帧/s（板上时间戳）。
- 修正前开机后第一次启动都进入这一状态（10-31 四次重启四次），与 2.5 的改动无关（原先的顺序同样是先 FIR、后增益模式）。

## 3. AGC

各通信体制的 AGC 配置与实测见 [`sw/matlab/README.md`](../sw/matlab/README.md)。要点：

- 板子设备树打开了快速 AGC 的"更强信号解锁"与 ADC / LMT 大过载解锁（驱动代码的默认值是关闭）。OFDM 的峰值可达锁定电平
  +10 dB，正好落在更强信号解锁的门限上，OFDM 接收时宜关闭更强信号解锁。
- 功率测量时长按 ClkRF 的采样计数（采样率的 4 倍）；慢速 AGC 的测量时长放不进两次增益更新间隔时，驱动会把它缩短。
- 快速 AGC 在信号到来前启动，会在噪声上以过高的增益锁定并保持；按包解锁在这两块板上不稳定。
- `adi,fagc-gain-index-type-after-exit-rx-mode` 在代码中 0 = 最大增益、1 = 设定增益、2 = 优化增益（驱动注释与此不同），
  且只在离开接收状态时生效。
- 驱动参数写入后一直有效，直到再改或板子重启；脚本改过的参数要在结束时恢复（MATLAB `glidelink.agcSetup` / `agcRestore`）。

## 4. 第三方软件

- MathWorks ADALM-Pluto 支持包可以直连板子，但按 12 位换算样点：读数大 16 倍、发射小 16 倍；采样率下限见 2.4。
- MathWorks 官方例程文件来自本机安装的支持包，不放进仓库（`glidelink.officialExample`）。

## 5. 尚未查明

- 2026-10-30 接收板出现过一次读 AD9361 时 PL 中 SPI 控制器的总线错误（内核 `synchronous external abort`，之后对 AD9361 的访问全部挂起，
  需复位），按同样步骤多次未复现。
- 两板之间的调频立体声广播（MathWorks FM 例程移植版，`source = "boards"`）解调后左声道信噪比约 25 dB，不随发射功率提高，
  不经射频时为 41.6 dB。
- 2026-10-31 脱机 DeepJSCC-Q 链路在同样衰减下，接收板 U1/U2 关闭时数据辅助 SNR 比打开时低 4～6 dB（额外衰减 20 dB：15 dB 对 22 dB）。
  打开 U1/U2 后 USB 链路会复位（1.1），对照测量被打断，只有一组可用；同期关闭发射时接收增益在 38～47 dB 之间变化，环境本身也在变。
  USB 3 链路常驻 U0 是否抬高 915 MHz 的底噪，尚未确定。
