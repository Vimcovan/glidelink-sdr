# GlideLink SDR 设计文档（草案 v0.1）

基于 PYNQ-ZU + AD9361 FMC 子卡的通信算法原型验证平台：板子接入 SoapySDR，先在 GNU Radio 中用软件验证算法，
再把算法逐个模块卸载到 PL，最终脱离 PC 运行。PL 侧参考 RFNoC 的思路，用户可以加入自己的 FPGA 模块。

本文给出总体架构、PL 外壳、用户模块接口规范、主机软件和开发流程，以及分阶段计划与待确认的问题。
数值与接口在第 0 阶段的验证后再定稿。

---

## 1. 目标与范围

### 1.1 目标

1. **作为普通 SDR 使用**：SoapySDR 设备，GNU Radio、SoapySDRUtil、CubicSDR 等现有工具可以直接收发。
2. **精细的射频控制**：除标准参数（频点、采样率、带宽、增益）外，AD9361 的驱动配置参数（如快速 AGC 的各项门限）
   和任意寄存器都能从 SoapySDR 接口访问。
3. **PL 用户模块**：用户按统一接口写 RTL 模块，放入 PL 的模块槽位；模块之间、模块与射频、模块与主机之间的连接
   由寄存器配置，不需要改外壳。
4. **逐步卸载**：同一个算法模块有软件参考实现（GNU Radio 块）和 PL 实现，二者接口与数值一致，可以逐比特比对；
   卸载后的模块在 GNU Radio 流程图中由代理块表示。
5. **脱机运行**：全部处理在 PL 中时，由板上 PS 的程序按配置建立连接、写模块参数并监视状态，不需要 PC。

### 1.2 不做的事（第一版）

- 不实现完整的 RFNoC：不用 CHDR 分组格式，不做多设备路由，不支持运行时动态改变 PL 内的模块种类。
  模块的增删需要重新生成比特流；运行时可以改变的是连接关系和模块参数。
- 不做多板时间同步（外部 10 MHz / PPS）。
- 部分重配置（DFX）留到后续版本评估。

## 2. 总体架构

```
                    ┌──────────────────────────── PL ─────────────────────────────────┐
  AD9361  ◄─LVDS──► │ axi_ad9361 ─► RX 流化 + 时间戳 ─┐        ┌─► TX 流化 + 时间戳 ─► axi_ad9361 │
  (FMC)             │   (D5 极性补丁, CTRL_OUT 寄存器)   │        │                              │
                    │                               ▼        │                              │
                    │                         ┌──────────────┴──┐                           │
                    │   用户模块槽位 0..N-1 ◄─►│  流交换（寄存器路由） │◄─► 主机端口：DMA ×M（收 / 发） │
                    │                         └─────────────────┘                           │
                    │   控制：AXI4-Lite 寄存器窗口（外壳 + 每个槽位 4 KB）                          │
                    └──────────────────────────────────────────────────────────────────┘
                                         ▲ AXI (HP / HPM)
  PS (Linux)  ad9361 驱动 + axi_dmac + IIO ─► libiio ─► Soapy 模块（SoapyGlideLink）
                                                         ├─ 板上：GNU Radio / Python / 脱机运行程序
                                                         └─ PC：libiio 网络后端（iiod）或 SoapyRemote
```

- 射频底层采用 ADI 的现成方案（HDL 的 `axi_ad9361`、Linux 的 ad9361 IIO 驱动、libiio），不再使用竞赛工程中自写的
  AD9361 初始化与接口。
- 平台自己实现的部分：RX / TX 流化与时间戳、流交换、模块槽位与寄存器窗口、主机端口、Soapy 模块、GNU Radio 代理块、
  脱机运行程序，以及模块开发的模板与比对流程。

## 3. 硬件与软件基础

| 项 | 选择 | 说明 |
|---|---|---|
| 开发板 | PYNQ-ZU（xczu5eg-sfvc784-2-e） | 与竞赛工程相同；FMC 引脚约束可沿用 |
| 射频 | AD9361 FMC 子卡（第三方卡，TX 数据线对 D5 的 P/N 在子卡上对调） | 也兼容 AD-FMCOMMS3（由拨码开关选择极性） |
| PL 射频接口 | ADI HDL `axi_ad9361` + `axi_dmac` + `util_cpack2` / `util_upack2` | 加入 D5 线对的 XOR 补丁（沿用竞赛工程 SW0 的做法） |
| 操作系统 | PYNQ 镜像（Ubuntu 22.04，内核 6.6.10-xilinx-v2024.1） | 驱动以外部模块 + 设备树叠加方式加入（见 7.1、第 10 节） |
| 驱动 | ADI Linux 的 ad9361、cf_axi_adc、cf_axi_dds；主线内核的 axi_dmac | |
| 用户态 | libiio + iiod、SoapySDR、GNU Radio 3.10 | |

## 4. PL 外壳

### 4.1 射频接口

- `axi_ad9361` 以 LVDS 模式工作，第一版 1R1T，之后扩展到 2R2T（流交换端口数随之增加）。
- TX 数据在进入 LVDS 输出前与线对掩码异或，掩码由 SW0 选通（竞赛工程 `ad9361_lvds_mode.v` 中 `TX_SWAP_PAIRS` 的做法），
  以兼容第三方卡与 FMCOMMS3。
- AD9361 的 `CTRL_OUT[7:0]`（AGC 锁定与增益索引等状态）接入外壳寄存器，供看门狗与监视程序不经 SPI 读取。
- AD9361 的 SPI、ENSM 控制引脚由 Linux 驱动管理（SPI 用 PL 中的 AXI Quad SPI，以设备树描述；PS 的两路 SPI 在 PYNQ-ZU 的启动配置下都不可用，见 `hw/README.md`）。

### 4.2 采样流化

`axi_ad9361` 的 ADC 侧以采样时钟输出带 valid 的数据，不能被反压；DAC 侧按采样时钟读取数据。外壳在两侧做适配：

- **RX 流化**：采样进入异步 FIFO，转为带反压的 AXI4-Stream，切成固定长度的包（长度可配置）。下游来不及接收时整包丢弃，
  并记入溢出计数器，同时在下一个包的标志中置位“此前有丢包”。
- **TX 流化**：AXI4-Stream 进入异步 FIFO，按采样时钟读出；FIFO 为空时输出 0，记入欠载计数器。
  带时间戳的包等到时间到达后才开始发送（4.3 节）。

### 4.3 时间戳

- 外壳中有一个 64 位采样计数器，在采样时钟下每个采样加 1，PS 可读写（用于对时）。
- RX：每个包的第一个采样附带它的计数值。
- TX：包可以带一个发送时刻；带时刻的包在计数器到达该值时开始送往 DAC，迟到的包按配置丢弃或立即发送，并记录。
- 时间戳使定时发送、收发对齐、TDD 突发成为可能，Soapy 的 `readStream` / `writeStream` 的 `timeNs` 由此换算。

### 4.4 流交换

- 端口：射频 RX（每通道 1 个源）、射频 TX（每通道 1 个汇）、用户模块槽位（每个槽位 1 个输入 1 个输出，可扩展）、
  主机端口（DMA，若干个收、若干个发）。
- 路由：每个汇端口有一个寄存器，选择它的数据来自哪个源端口；同一时刻一个源只接一个汇（第一版不做一对多复制）。
  路由在包边界生效，不会切断半个包。
- 实现：基于 AXI4-Stream Switch（Xilinx IP，寄存器路由模式）或自写的多路选择器，在第 0 阶段比较资源与时序后决定。
- 这样，任意一个模块的输入、输出都可以接到主机端口，用于把一个模块单独拿出来与软件版比对（第 6 节）。

### 4.5 主机端口

- 射频 RX / TX 与主机之间：沿用 ADI 的 `axi_dmac` + IIO 缓冲区，libiio 的标准收发路径，GNU Radio 与 Soapy 现有工具可直接使用。
- 模块端口与主机之间（不经射频的流）：需要一条通用的 DMA 流通路。两个候选，在第 0 阶段验证：
  1. 再例化 `axi_dmac`，以 ADI 的通用 IIO DMA 缓冲设备或自写的小驱动挂到 IIO，使 libiio 统一访问；
  2. Xilinx AXI DMA + udmabuf，在用户态管理缓冲区（竞赛工程用过的方式）。
- 主机端口的个数决定能同时“开窗”观察的位置数，第一版定为收、发各 2 个。

### 4.6 时钟

- 用户模块统一工作在一个处理时钟（暂定 200 MHz，第 0 阶段确定），跨时钟域全部在外壳内完成，模块不接触采样时钟。
- 采样率最高按 AD9361 的 61.44 MSPS 设计，单通道 sc16 数据率约 246 MB/s，处理时钟与 32 位数据宽度下有足够余量。

### 4.7 寄存器地址空间（草案）

| 偏移 | 内容 |
|---|---|
| 0x0000 | 外壳：ID、版本、能力（通道数、槽位数、主机端口数）、计数器（溢出、欠载、迟到包）、时间戳计数器、`CTRL_OUT` |
| 0x1000 | 流交换路由寄存器 |
| 0x2000 + 0x1000·k | 第 k 个用户模块槽位的寄存器窗口（4 KB） |

`axi_ad9361`、`axi_dmac` 的寄存器在各自的地址上，由驱动访问。

## 5. 用户模块接口规范

### 5.1 端口

| 端口 | 说明 |
|---|---|
| `clk`、`rst_n` | 处理时钟与同步复位 |
| `s_axis_*` | 输入流：`tdata[31:0]`、`tvalid`、`tready`、`tlast`、`tuser` |
| `m_axis_*` | 输出流：同上 |
| `s_axil_*` | AXI4-Lite 从接口，4 KB 地址窗口 |

- 数据：默认每拍一个复采样，`tdata = {Q[15:0], I[15:0]}`，16 位补码（sc16），与 SoapySDR 的 CS16 格式一致。
  模块也可以在包内传别的数据（比特、软比特、字节），格式由模块的说明文件声明，主机侧按声明解释。
- 包：`tlast` 标记包的最后一拍。`tuser` 第一版定为 `{flags[7:0], timestamp[63:0]}`，只在包的第一拍有效；
  flags 位 0 = 此前有丢包，位 1 = 突发结束，位 2 = 定时发送（到达 RF TX 时按时间戳发出），其余保留。
  不关心时间的模块原样传递或忽略。
- 反压：模块必须遵守 AXI4-Stream 握手，输入、输出两侧都可能被反压。

### 5.2 寄存器

- 窗口前 16 字节为标准寄存器：模块 ID、版本、控制（使能、软复位）、状态。其余由模块自定义。
- 每个寄存器在模块说明文件中给出名字、位域、默认值与含义；Soapy 模块和代理块按名字访问，不直接写地址。

### 5.3 每个模块需要附带的内容

| 内容 | 作用 |
|---|---|
| RTL 与模块说明文件（YAML：端口数据格式、寄存器、资源估计） | 构建与主机侧解释 |
| 参考模型（Python / NumPy） | 规定逐比特的数值行为，是 RTL 的比对基准 |
| GNU Radio 块（调用参考模型，或等价的 C++ 实现） | 软件原型阶段使用 |
| GNU Radio 代理块 | 卸载后在流程图中代表 PL 模块：配置路由与寄存器，不处理数据 |
| 测试向量与仿真测试平台 | 仿真比对 |

平台提供模板生成上述文件的骨架。

## 6. 开发流程：从软件原型到 PL

| 阶段 | 处理位置 | PC 与板子之间的数据 |
|---|---|---|
| 0 | 全部在 GNU Radio | 原始 I/Q（千兆网，单方向约 10～15 MSPS 为宜） |
| 1 | 部分模块在 PL，其余在 GNU Radio | 中间结果 |
| 2 | 全部在 PL，PS 运行脱机程序 | 无 |

单个模块从软件到 PL 的步骤：

1. 在 GNU Radio 中用软件块验证算法；
2. 按 5.3 节写出参考模型，使软件块与参考模型逐比特一致；
3. 写 RTL，仿真中与参考模型逐比特比对；
4. 上板硬件在环比对：主机端口把同一段数据送进 PL 模块，取回输出，与参考模型的输出逐比特比较；
5. 在流程图中把软件块换成代理块，前后相邻的 PL 模块之间的数据不再经过主机。

这一流程即竞赛工程中“整数参考模型 + RTL 逐比特比对”的做法，作为平台的标准流程。

## 7. 主机软件

### 7.1 内核与驱动

- 从与 PYNQ 内核版本匹配的 ADI Linux 源码中，以外部模块方式编译 ad9361、cf_axi_adc、cf_axi_dds 等驱动
  （竞赛工程为 Mali-400 补编 lima 驱动时用过同样的方法）。
- 设备树以叠加方式在加载比特流后写入 configfs（`hw/scripts/load_overlay.sh`），描述 SPI 上的 AD9361、`axi_ad9361`、
  `axi_dmac` 与参考时钟。
- AD9361 的初始配置（快速 AGC 参数、锁定电平 −14 dBFS 等）写进设备树，沿用竞赛工程中验证过的取值。

### 7.2 Soapy 模块 SoapyGlideLink

基于 libiio，在板上（本地上下文）和 PC 上（网络上下文，经板上的 iiod）都能运行。控制分三层映射：

| 层级 | 内容 | Soapy 接口 |
|---|---|---|
| 标准参数 | 频点、采样率、带宽、增益模式、手动增益、校准 | `setFrequency`、`setSampleRate`、`setBandwidth`、`setGainMode`、`setGain` 等 |
| 驱动配置参数 | 驱动在 debugfs 中给出的设备树参数（如 `adi,fagc-*`），写入后经 `initialize` 重新初始化 | `writeSetting` / `readSetting`（名字与设备树属性一致），另有 `initialize` 设置项 |
| 原始寄存器 | AD9361 任意 SPI 寄存器；外壳与模块寄存器 | `writeRegister` / `readRegister`，接口名 `AD9361`、`FPGA`；模块寄存器另提供按名字访问的设置项 |

- 流：`setupStream` 支持射频 RX / TX 与模块主机端口，格式 CS16（另提供 CF32 转换），支持时间戳与突发标志。
- 驱动会在部分操作（改采样率、切换增益模式等）时重写相关寄存器；直接写入的寄存器值可能被覆盖。
  文档中注明哪些操作会重写哪些寄存器，长期使用的设置放在驱动配置参数一层。

### 7.3 GNU Radio

- 射频收发用 GNU Radio 自带的 Soapy 源 / 汇（`gr-soapy`）。
- OOT 模块 `gr-glidelink`：连接管理块（建立 PL 内的路由）、各模块的代理块、主机端口源 / 汇、寄存器设置块。

### 7.4 脱机运行

- 连接关系与模块参数写在一个配置文件（YAML）中；板上的守护程序读取配置、建立路由、写寄存器、监视计数器，由 systemd 启动。
- 配置文件可以由第 1 阶段的 GNU Radio 流程图导出，使原型与脱机运行使用同一套连接描述。

## 9. 分阶段计划与验收标准

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| 0：射频底座 | ADI HDL 移植到 PYNQ-ZU（含 D5 补丁）；驱动编译与设备树叠加；libiio 跑通 | `iio_info` 列出设备；SoapySDRUtil 探测到设备并收发；GNU Radio 中看到频谱，两板之间能传一个已知波形 |
| 1：外壳 | RX / TX 流化、时间戳、流交换、主机端口、寄存器窗口；一个直通模块槽位 | 指定时刻发送的突发在 RX 时间戳上对齐；长时间运行的溢出 / 欠载计数为 0（在声明的采样率下） |
| 2：Soapy 与 GNU Radio | SoapyGlideLink 三层控制；`gr-glidelink` 连接管理与代理块 | 在 GNU Radio 中修改快速 AGC 参数并重新初始化；读写任意 AD9361 寄存器；PC 经网络使用板子 |
| 3：第一个模块 | NCO、FIR，走完第 6 节流程 | 仿真与上板硬件在环比对均逐比特一致；代理块替换后流程图输出不变 |
| 4：迁移竞赛模块 | 同步、OFDM、DeepJSCC 作为用户模块 | 原竞赛系统在平台上以脱机方式运行，指标与竞赛版本相当 |
| 5：文档与模板 | 模块模板、教程 | 按教程从零写一个新模块并在 GNU Radio 中调用 |

## 10. 风险与待确认的问题

1. **驱动与内核版本**：ADI 的驱动需要与 PYNQ 内核（6.6.10）匹配的源码分支，cf_axi_adc / dds 等只在 ADI 的内核树中。
   若补编困难，备选是换用 ADI 的 Kuiper Linux 镜像（驱动齐全，但失去 PYNQ 环境）。第 0 阶段首先验证。
2. **HDL 与 Vivado 版本**：ADI HDL 的发布分支只在指定版本的 Vivado 上测试，本机为 Vivado 2025.2；需要选择匹配的分支，
   或在版本检查上做处理并自行验证。
3. **模块主机端口的 DMA 通路**（4.5 节）：两个候选方案需要原型验证。
4. **网络带宽**：千兆网限制第 0 阶段的原始 I/Q 速率；高采样率下需要尽早把前端模块卸载到 PL。
5. **AGC 看门狗**：竞赛工程中的看门狗针对 20 MSPS 下快速 AGC 偶发不解锁的现象；在新驱动下是否仍需要，第 0 阶段复测后决定。
6. **流交换规模**：槽位与端口数增加时的资源与时序，第 1 阶段评估。
